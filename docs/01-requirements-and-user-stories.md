# 01 Requirements and User Stories

## Course Basis

The EBU6304 slides on requirements and agile development emphasise that software engineering is not just about writing code, but about reducing the risk of misunderstanding through traceable requirements, user stories, acceptance criteria, and iterative feedback. For QM HIRE, the requirements document needs to answer four questions: who uses the system, what they need to accomplish, under what conditions a task is considered complete, and which non-functional constraints influence the design.

## Stakeholders

| Stakeholder | Goal | Main concerns |
|---|---|---|
| TA applicant | Find suitable TA vacancies, maintain resumes, submit applications, and track offers | Usability, transparent application status, privacy, and secure resume upload |
| Module Organiser (MO) | Publish vacancies, screen applicants, review matching analysis, and send offers or rejections | Vacancy lifecycle, candidate ranking, workload constraints, and explainable decisions |
| Administrator | Manage users, skill catalogue, audit logs, and workload | Access control, auditability, data consistency, and maintenance efficiency |
| Course staff / assessor | Evaluate whether the course project satisfies software engineering requirements | Requirements traceability, design quality, testing evidence, ethics, and safety |
| Maintainer | Fix, extend, and deploy the system in the future | Module boundaries, configuration management, testability, and run instructions |

## Glossary

| Term | Definition |
|---|---|
| TA | Teaching Assistant, the student applicant role |
| MO | Module Organiser, the teacher or course leader responsible for publishing and reviewing TA vacancies |
| Vacancy / Job | A TA position that can be applied for, including course information, schedule, slots, and skill requirements |
| Resume | A version of a TA’s resume, which may include uploaded files and skill records |
| Application | A TA’s application to a vacancy, including status, cover letter, and a resume snapshot |
| Match score | A matching analysis generated by the system based on skills, workload, and optional AI results |
| Workload record | A TA workload record created from an accepted position |
| Audit log | An audit record of key management actions, status changes, and AI requests |
| AI consent | The user’s explicit agreement to data being sent and used for assistance before triggering AI functions |

## Product Scope

### In Scope

- TA self-registration, login, personal settings, resume management, and job applications.
- MO creation, editing, publishing, and cancellation of vacancies, as well as application review.
- Admin management of users, skills, audit logs, database demo pages, and workload monitoring.
- JSON file persistence to satisfy coursework demonstration needs and the no-external-database deployment constraint.
- Optional Qwen/DashScope AI assistance, including resume suggestions, job matching, candidate ranking, and writing support.
- Core security capabilities: RBAC, CSRF protection, defensive file upload, session hardening, AI consent, and auditing.

### Out of Scope

- Real university identity authentication, email delivery, payment, or integration with official HR systems.
- Multi-node high-availability deployment and distributed transactions.
- Fully automated hiring decisions made by AI.
- A production-grade public compliance archive system.

## Functional Requirements

| ID | Requirement | Primary users | Current implementation evidence | Acceptance criteria |
|---|---|---|---|---|
| FR-01 | Users can register, log in, log out, and maintain personal settings | TA, MO, Admin | `RegisterServlet`, `LoginServlet`, `LogoutServlet`, `SettingsServlet`, `AuthService`, `TaAccountService` | TA self-registration can only create a TA account; session is rotated after successful login; protected pages redirect to login after logout |
| FR-02 | TAs can create, upload, duplicate, edit, and delete resumes | TA | `ResumesServlet`, `ResumeService`, `ResumeFileUpload` | Valid files are saved into the data directory; illegal extensions, MIME types, file signatures, or oversized files are rejected |
| FR-03 | TAs can browse, filter, favourite vacancies, and submit applications | TA | `VacanciesServlet`, `VacancyDetailServlet`, `FavoritesServlet`, `ApplicationSubmitServlet` | Only published and open vacancies can be applied for; duplicate applications are prevented; application submission stores a resume snapshot |
| FR-04 | TAs can track applications, withdraw pending applications, and accept or reject offers | TA | `ApplicationsServlet`, `ApplicationDecisionServlet`, `ApplicationService` | Status transitions must follow business rules; unauthorised actions are rejected |
| FR-05 | MOs can create, edit, publish, cancel vacancies, and maintain skill requirements | MO | `VacancyCreateServlet`, `VacancyEditServlet`, `JobService`, `JobRequirementRepository` | An MO can only manage their own vacancies; cancelling a vacancy updates related application states |
| FR-06 | MOs can review applications, view matching analysis, download submitted resume snapshots, and send decisions | MO | `ApplicationDetailServlet`, `MatchAnalysisServlet`, `MatchingService`, `ApplicationSubmissionFiles` | An MO can only review applications for their own vacancies; matching analysis can be refreshed in the review flow; final decisions are always made by a human |
| FR-07 | Admins can manage users, skills, audit logs, database demo pages, and workload | Admin | `AdminUsersServlet`, `AdminSkillsServlet`, `AdminAuditServlet`, `DbDemoServlet`, `WorkloadsServlet`, `AdminService` | `/admin/*` and `/workloads` are role-protected; the database demo page is available at `/admin/database` |
| FR-08 | The system provides optional AI support when an AI key is configured, and falls back to rule-based behaviour when it is not | TA, MO | `QwenAiService`, `AiRequestGuard`, AI servlets, `MatchingService` | Requests are rejected if AI consent is not given; the core recruitment flow must still run when AI is unavailable |
| FR-09 | The system records audit logs for key state changes and AI requests | MO, Admin, Maintainer | `AuditLogRepository`, `AdminAuditServlet`, `AuditAction` | User creation, vacancy changes, application state changes, AI requests, and similar events can be searched in the audit page |
| FR-10 | The system persists recruitment data in JSON files and guarantees consistent read/write behaviour within a single JVM | All | `TaDatabase`, `FileTaDatabase`, `JsonTableStore`, `AtomicJsonFileWriter` | An empty data directory is automatically initialised; save operations use atomic writes; tests can isolate persistence through temporary data directories |

## Non-Functional Requirements

| ID | Quality attribute | Requirement | Evidence | Priority |
|---|---|---|---|---|
| NFR-01 | Security | Protected pages must require login; sensitive functions must check role and ownership | `AuthFilter`, role checks in servlets and services | High |
| NFR-02 | Security | All unsafe HTTP requests must pass CSRF validation | `CsrfFilter`, `CsrfTokens`, JSP token injection | High |
| NFR-03 | Security | File uploads must restrict size, extension, MIME type, and file signature | `ResumeFileUpload`, `ResumeFileUploadTest` | High |
| NFR-04 | Privacy | AI functions must require explicit consent and must not log full prompts or model outputs | `AiRequestGuard`, `AuditAction.AI_REQUEST` | High |
| NFR-05 | Maintainability | Clear separation between Web, Service, Persistence, and Domain layers | `web/servlet`, `service`, `db`, `domain` packages | High |
| NFR-06 | Reliability | Data writes should avoid partial writes and corruption | `AtomicJsonFileWriter`, `JsonTableStore` | High |
| NFR-07 | Testability | Core business logic, repositories, filters, servlets, and utility classes should have automated tests | `src/test/java` | High |
| NFR-08 | Usability | Main TA, MO, and Admin workflows should be reachable from the post-login sidebar or page entry points | JSP portal pages, README route table | Medium |
| NFR-09 | Portability | The system should run on Java 17, Maven, and Tomcat 11 without an external database | `pom.xml`, `README.md`, `AppConfig` | Medium |
| NFR-10 | Performance | Pages and matching analysis should respond interactively under coursework-scale data | Small JSON dataset, repository in-memory snapshots | Medium |

## User Stories And Acceptance Criteria

### TA Applicant Stories

| ID | User story | Acceptance criteria | Trace |
|---|---|---|---|
| US-TA-01 | As a TA, I want to self-register an account so that I can start applying for vacancies | Only a TA role can be created; email must be unique; weak or mismatched passwords are rejected | FR-01, `RegisterServletTest` |
| US-TA-02 | As a TA, I want to maintain multiple resume versions so that I can apply for different vacancies | I can create, edit, duplicate, and delete unlocked resumes; skills and availability can be saved | FR-02, `ResumeServiceTest` |
| US-TA-03 | As a TA, I want to upload PDF/DOC/DOCX resumes so that MOs can view my formal file | Only allowed file types are accepted; files are stored inside the data directory; a snapshot is created on submission | FR-02, FR-03, `ResumeFileUploadTest` |
| US-TA-04 | As a TA, I want to browse and favourite open vacancies so that I can compare opportunities | I can view open vacancies, filter them, favourite them, and remove favourites | FR-03 |
| US-TA-05 | As a TA, I want to submit applications and track their status so that I know what to do next | Application states show pending/reviewing/offered/accepted/rejected/withdrawn/declined; pending applications can be withdrawn | FR-03, FR-04, `ApplicationServiceTest` |
| US-TA-06 | As a TA, I want to use AI resume suggestions after giving consent so that I can improve my materials | Requests fail if AI consent is not checked; after consent, AI only gives suggestions and does not submit applications automatically | FR-08, `AiRequestGuardTest` |

### MO Stories

| ID | User story | Acceptance criteria | Trace |
|---|---|---|---|
| US-MO-01 | As an MO, I want to publish and maintain vacancies so that I can recruit suitable TAs | I can create draft/open vacancies; I can only edit my own vacancies; cancelling a vacancy updates related applications | FR-05, `JobServiceTest` |
| US-MO-02 | As an MO, I want to define skill requirements so that candidate matching has a clear basis | I can add required/preferred skills and proficiency requirements to a vacancy | FR-05, `JobRequirementRepository` |
| US-MO-03 | As an MO, I want to view application details and the submitted resume snapshot so that I can review fairly | I can only view applications for my own vacancies; the downloaded file is the submission-time snapshot and is not affected by later TA resume edits | FR-06, `ApplicationSubmissionFilesTest` |
| US-MO-04 | As an MO, I want to refresh matching analysis and view the explanation so that it supports but does not replace my decision | I can refresh analysis in the review flow; it shows rule-based score, AI/fallback score, missing skills, and recommendation explanation; final offer/reject actions are always triggered by the MO | FR-06, FR-08, `MatchingServiceTest` |

### Admin Stories

| ID | User story | Acceptance criteria | Trace |
|---|---|---|---|
| US-AD-01 | As an Admin, I want to manage users so that I can create MO/Admin accounts or maintain TA accounts | I can create role-based accounts, edit profiles, reset passwords, and deactivate non-admin users; actions are logged in the audit trail | FR-07, `AdminUsersServletTest` |
| US-AD-02 | As an Admin, I want to maintain the skill catalogue so that vacancies and resumes use consistent terminology | Referenced skills are protected; create and update actions are auditable | FR-07 |
| US-AD-03 | As an Admin, I want to view workload so that I can identify overloaded TAs | I can view accepted workload, weekly hours, capacity, estimated income, and rebalancing suggestions | FR-07, `AdminServiceTest` |
| US-AD-04 | As an Admin, I want to access the database demo page so that I can inspect the coursework JSON data layer | `/admin/database` is only accessible to Admin; non-admin users receive forbidden | FR-07, `DbDemoServlet` |
